Adaptive Property Intelligence: From Property Data to Intent-Aware Decisions

Watchdog Intelligence is not a layer that summarizes property records. It is a governed research assistant that learns what the user is trying to accomplish, reasons over concrete property evidence, asks the smallest useful questions, updates its understanding as the user works, and changes the analysis accordingly.

Observe real behaviorReason from governed evidenceAsk high-value questionsRemember confirmed intentRecommend the next useful action
01 · PRODUCT THESIS

Intelligence begins when the same property means something different to different people.

A tax figure, sale record, permit event, listing status, assessment anomaly, comparable sale, ownership duration, or price change is not inherently an insight. It becomes useful only in the context of the user's profession, objective, stage of work, other properties under review, prior questions, and the decisions they are trying to make.

The core Watchdog question is not “What data do we have?” It is “What is this user trying to decide, what evidence materially changes that decision, what do we still need to know, and what is the smallest question that will improve the answer?”

Five requirements

  • Concrete: insights must use real governed property facts whenever available.
  • Contextual: profession alone is not enough. Watchdog must learn the job-to-be-done.
  • Adaptive: analysis changes as the user answers questions, saves properties, compares records, revisits a property, creates reports, or takes actions.
  • Explainable: the system distinguishes observed facts, derived findings, hypotheses, user-confirmed intent, assumptions, and missing evidence.
  • Useful: output should improve a real decision, conversation, workflow, financial model, diligence process, or next action.
02 · THE INTENT ENGINE

Observe → hypothesize → ask → update → analyze → learn.

Watchdog should maintain a continuously updated, governed intent model for each signed-in user and for each active research context. The intent model is not a hidden personality profile. It is an auditable record of what Watchdog currently believes the user is trying to accomplish and why.

Signals Watchdog may use

Explicit profession, saved/watchlisted properties, property mix, active page, searches, comparisons, repeated visits, reports created, questions asked, models opened, changes monitored, listing/market status where lawfully available, geographic clustering, time horizon, user-confirmed objectives, and prior corrected assumptions.

A hypothesis is not a fact

If five of ten saved properties appear actively listed, Watchdog may reasonably infer that the user could be comparing active inventory, working with buyers, screening investments, or monitoring a farm. It must not silently pick one and behave as though it was confirmed. It should record the observation, create competing hypotheses, assign confidence, and ask a question that separates them.

High-information-gain question

“I noticed that 5 of the 10 properties you are watching are currently listed. Are you comparing homes for a buyer, monitoring a farm for listing opportunities, screening investment inventory, or something else?”

03 · QUESTIONING POLICY

Ask less, learn faster.

A human assistant does not repeatedly ask the user to fill out a profile. They notice patterns, remember answers, and ask a timely question when the answer will materially change the work. Watchdog should do the same.

Ask whenTwo or more plausible intents would produce materially different analysis or next actions.
Do not ask whenThe answer is already confirmed, can be derived safely from governed facts, or would not change the output.
PreferOne discriminating question with concrete choices and an “other” path.
AvoidLong questionnaires, repeated onboarding, manufactured certainty, and questions whose answer Watchdog already knows.

Intent confidence

Every inferred intent should carry a confidence score and supporting evidence. User confirmation should outweigh behavioral inference. User correction should immediately reduce or replace the prior hypothesis and be logged as a correction event.

04 · REAL ESTATE AGENT USE CASE

An agent is not one use case.

“Real estate agent” only establishes a professional lens. Watchdog still needs to discover whether the user is farming for listings, working buyers, preparing a listing appointment, researching a sphere contact, prospecting absentee owners, evaluating a price reduction, studying market movement, or performing another task.

Farming for listings

For an agent whose behavior suggests geographic farming, Watchdog should surface evidence that can create an ethical, relevant homeowner conversation: ownership duration, current listing status, prior sale history, assessment/tax changes, permit/change events, market context, nearby listing/sale patterns, equity context when based on defensible inputs, and other property-specific reasons to start a conversation. It should help answer “Why might this homeowner be worth contacting now?” without claiming the homeowner intends to sell.

Example assistant behavior

“You have opened 18 owner-occupied properties in the same ZIP this week and saved 11. Are you building a listing farm? If yes, I can rank these properties by evidence-backed conversation opportunity and show you the fact behind each ranking.”

Buyer representation

When the user appears to be researching active or candidate homes for a buyer, Watchdog should pivot away from prospecting language and toward decision support: comparable properties, tax carrying costs, assessment context, price history, sale chronology, permits, property changes, neighborhood/town context, potential diligence exceptions, competing inventory, and evidence not obvious from the listing presentation.

Example assistant behavior

“These saved properties look like a buyer shortlist rather than a farm. Should I compare them on purchase price context, taxes, nearby sales, property changes, and diligence risk, or are you researching them for another reason?”

05 · WATCHLIST AS RESEARCH MEMORY

A watchlist is evidence of research, not merely a folder.

Watchdog should analyze the watchlist as a set. The mix of properties, geographic concentration, listing status, recency, repeated opens, user notes, changes, and actions can reveal the likely research job. The system should use those signals to improve the questions it asks and the intelligence it prioritizes.

06 · GOVERNED MEMORY & LOGGING

Log everything needed to reconstruct why Watchdog acted.

Human-feeling assistance requires memory. Trustworthy assistance requires that memory to be explicit, scoped, and inspectable. Watchdog should keep a structured decision history rather than an opaque transcript-only memory.

Minimum event trail

  • Observed user action or property signal.
  • Source and timestamp for external/property facts.
  • Hypotheses considered and confidence before questioning.
  • Question asked and why it was selected.
  • User answer, correction, skip, or non-response.
  • Intent confidence after the answer.
  • Models/findings/evidence used in the resulting analysis.
  • Recommendation produced and whether it was shown, opened, dismissed, saved, exported, or acted upon.
  • Outcome feedback where the user later provides it.

The logging principle is reconstructability, not indiscriminate surveillance. Watchdog should capture product actions and decision evidence needed to improve the assistant while avoiding unnecessary sensitive information. Authorization, RLS, retention, privacy, and data-minimization boundaries remain first-class controls.

07 · LIVE MARKET & EXTERNAL DATA

Fresh outside signals can improve intent detection, but data rights remain part of the intelligence.

Listing status and market context are high-value signals for Watchdog. They should come from permitted, attributable sources or licensed integrations. Watchdog should never imply MLS completeness when an MLS feed is not available, and should never turn an uncertain third-party observation into a confirmed fact.

BoldTrail integration opportunity

If the owner's BoldTrail API access exposes the relevant CRM, contact, listing, search, or market endpoints, Watchdog can ingest that data through a server-side adapter, normalize it into the governed data layer, attach source/freshness metadata, and make it available to the Intent Engine and Analyst. Credentials must remain server-side. The exact scope depends on the API access and documentation available to this account.

No installed BoldTrail plugin is currently available in this ChatGPT workspace, so the likely path is direct documented API integration through the Watchdog backend rather than a ChatGPT plugin. External listing sources such as Zillow or others should be used only through access methods and terms that permit the intended use.

08 · PROPOSED ARCHITECTURE

The Context Graph sits between raw evidence and the Analyst.

  1. Truth Layer: governed property facts, sources, freshness, normalized events.
  2. Behavior Event Layer: signed-in product actions relevant to current research.
  3. Context Graph: user profession + property set + active task + confirmed intent + candidate intents + evidence + missing information.
  4. Intent Engine: updates hypotheses and selects high-information-gain questions.
  5. Intelligence Models: deterministic/validated models produce evidence-backed findings.
  6. Watchdog Analyst: explains, compares, asks, challenges, and recommends using only authorized context.
  7. Action Layer: reports, cases, watchlists, CRM tasks, alerts, exports, workflows.
  8. Learning Layer: logs corrections, outcomes, usefulness and model/product feedback without converting unsupported behavior into truth.
A useful internal object is an Intent State: profession, active job-to-be-done, candidate jobs, confidence, evidence references, user-confirmed fields, assumptions, missing questions, property scope, source freshness, and last meaningful update.
09 · DESIGN PRINCIPLES

What makes Watchdog feel human without pretending to be human.

  • Remember what the user already told us.
  • Notice meaningful patterns across properties, not just within one record.
  • Ask a question when the answer will change the analysis.
  • Explain the observation behind the question.
  • Separate fact, inference, assumption, and user-confirmed intent visually and in logs.
  • Admit uncertainty and missing evidence.
  • Do not manufacture urgency, seller motivation, ROI, legal conclusions, valuation conclusions, or protected/sensitive attributes.
  • Allow the user to correct Watchdog quickly and make the correction durable.
  • Change the workspace as intent becomes clear. A farm should not feel like a buyer shortlist; a buyer shortlist should not feel like an appeal file.
  • Measure usefulness by better decisions and completed workflows, not by number of AI messages.
10 · NORTH-STAR EXPERIENCE

Watchdog should know enough to be useful, but never so much that it stops asking.

The north-star experience is a user opening Watchdog and feeling that the system understands the work already in progress: the properties being researched, what changed, why those changes matter to this profession and task, what Watchdog still does not understand, and the one or two questions that will most improve the next decision.

North-star prompt

“I think you're building a South Jersey listing farm. You saved 14 properties in the same market, most are not actively listed, and you have repeatedly opened ownership, tax, and change history. I'm 68% confident. Is that what you're doing? If yes, I can rank the farm by evidence-backed conversation opportunity and tell you exactly why each owner made the list.”

That is materially different from “Here is the tax assessment.” It is the difference between a data product and an intelligence system.
